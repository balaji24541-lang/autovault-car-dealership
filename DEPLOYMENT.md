# AutoVault deployment guide

This repository is prepared for a Vercel frontend, Render FastAPI service, and Render PostgreSQL database. The deployment has **not** been created: connecting accounts, provisioning the database, and publishing the site require the owner's approval. No production URL exists yet.

## Before provisioning

1. Push this reviewed branch to GitHub only after you approve the push. Preserve the existing history.
2. Sign in to [Vercel](https://vercel.com/) and import the GitHub repository. Set the frontend root directory and build settings below, then deploy once to obtain the actual Vercel production origin. This first frontend deploy will not reach the API yet.
3. Sign in to [Render](https://render.com/) with your own account. In Render, create a Blueprint from the repository's `render.yaml`. Enter the actual Vercel origin for `CORS_ORIGINS`, supply the demo account settings below, and review all resources before applying it. The current blueprint selects free Render resources. A free Render PostgreSQL database expires after 30 days; for a longer-lived interview demo, choose an appropriate paid PostgreSQL plan yourself before provisioning. No resource is created by this repository change.
4. After Render assigns the API's actual URL, set it as Vercel's production `VITE_API_URL` and redeploy the frontend. Verify customer/admin flows, then add the real Vercel URL to README's Live Demo link.

## Render API and database

The Blueprint sets the web service root directory to `backend`, installs `requirements.txt`, runs the idempotent demo seed, then starts FastAPI with Uvicorn on Render's `$PORT`. It links `DATABASE_URL` to the managed database's internal connection string. The application normalizes Render's PostgreSQL URL to SQLAlchemy's installed psycopg 3 driver.

Set the requested backend environment values in Render:

| Variable | Value |
| --- | --- |
| `DATABASE_URL` | Populated by the Blueprint from the managed PostgreSQL resource. Do not replace it with a local URL. |
| `JWT_SECRET` | Generated by Render in the Blueprint; keep private and at least 32 random bytes. If setting it manually, generate with `python -c "import secrets; print(secrets.token_urlsafe(48))"` and paste directly into Render. |
| `CORS_ORIGINS` | Exact production Vercel origin, e.g. `https://your-project.vercel.app`; no path or trailing slash. Add a preview origin only if it is intended to call this API. Wildcards are rejected. |
| `DEMO_CUSTOMER_EMAIL` | `demo.customer@example.com` |
| `DEMO_CUSTOMER_PASSWORD` | `AutoVault-Demo-Customer-2026!` |
| `DEMO_ADMIN_EMAIL` | `demo.admin@example.com` |
| `DEMO_ADMIN_PASSWORD` | `AutoVault-Demo-Admin-2026!` |

The two demo passwords above are deliberately public, non-sensitive credentials for this disposable demo only. Enter them in **Render backend environment settings**; never put JWT/database values or these admin credentials in Vercel settings or client-side source. Anyone can use the public admin demo account to change demo inventory. Do not use these accounts or passwords for any personal or production system. To rotate a demo password, update the existing account through a controlled backend/database operation; the seeder deliberately refuses to reset an existing password or change an existing role.

At startup, SQLAlchemy `create_all` adds missing tables without dropping tables or rows. The seed uses a PostgreSQL advisory lock and adds only absent demo users and vehicle records. Repeated deploys preserve existing records and stock. There is no schema migration framework yet; use reviewed, additive migrations for future schema changes.

After the Render deploy, copy the service's actual `onrender.com` origin. Check `https://<actual-service>.onrender.com/docs` and `https://<actual-service>.onrender.com/openapi.json`; replace angle-bracket placeholders only with the URL Render actually assigned.

## Vercel frontend

1. Import the same GitHub repository in Vercel.
2. Set **Root Directory** to `frontend` (the `vercel.json` in that directory supplies the Vite build command and `dist` output settings).
3. Set `VITE_API_URL` in the Vercel Production environment to the actual Render service origin, e.g. `https://<actual-service>.onrender.com` (no trailing slash, and no `/api` suffix).
4. Deploy after the Render API is available. `VITE_API_URL` is public frontend configuration, not a place for secrets. Never set `JWT_SECRET`, `DATABASE_URL`, demo passwords, or other privileged values in Vercel.
5. Copy Vercel's actual production origin and set it as Render's `CORS_ORIGINS`. Redeploy/restart the Render service after changing CORS. If you change the Vercel domain later, update CORS to match exactly.

The frontend's API helper joins `VITE_API_URL` with `/api/...`. For local Vite development without that variable, `/api` is proxied to `http://localhost:8000`; Docker Compose explicitly sets the browser-facing local API origin.

## Demo evaluator flow

Once both services are deployed and the CORS origin is configured, place the real Vercel production URL in the README's **Live Demo** link. Evaluators can then use:

- Customer: `demo.customer@example.com` / `AutoVault-Demo-Customer-2026!`
- Admin: `demo.admin@example.com` / `AutoVault-Demo-Admin-2026!`

The customer can browse, search, filter, and purchase vehicles. The admin can add, edit, delete, and restock demo inventory. Purchases only decrement demo stock; there is no payment processing. The demo database can be modified by evaluators, so reseeding will add missing sample rows but will not restore changed stock or overwrite existing data.

## Deployment verification

After you approve and complete the provider setup, verify:

1. Render reports the PostgreSQL database available and the API service live.
2. The API `/openapi.json` responds and the backend logs contain no startup/seed errors.
3. The Vercel production URL loads over HTTPS.
4. Sign in with both demo roles; check vehicle listing, search/category/price filters, one customer purchase, and admin create/edit/restock/delete controls.
5. Confirm the browser console and network panel show successful API calls and no CORS errors.
6. Restart/redeploy the API and verify the accounts and inventory still exist. Do not delete the database or use a reset operation as a persistence test.
7. Update README with the verified real URL. Until these steps are completed, the project has no public live demo.
